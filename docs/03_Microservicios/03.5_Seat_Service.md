# Seat Service (Inventario y Reservas)

## 1. Responsabilidad
Administrar la distribución física y el estado de cada asiento en tiempo real, garantizando la consistencia y previniendo colisiones durante el proceso de compra de boletos. No administra pagos de forma directa, pero maneja la validación concurrente (Optimistic Locking) de la transacción.

## 2. Stack Tecnológico
*   **Lenguaje:** Java 17
*   **Framework:** Spring Boot 4
*   **Base de Datos:** PostgreSQL 15 (vía Spring Data JPA)
*   **Migraciones:** Flyway
*   **Mensajería:** RabbitMQ (Para arquitectura SAGA y Cancelaciones)

## 3. Dependencias Inter-servicio
*   **Llamadas Salientes (Outbound):** 
    *   Llamadas Síncronas (REST) al `Showtime Service` para validar si una función está en estado `PROGRAMADA` antes de permitir la compra o bloqueo de una butaca.
*   **Llamadas Entrantes (Inbound):** 
    *   Síncronas: Recibe peticiones del **API Gateway** (para consultar o bloquear butacas) y del **Showtime Service** (para pre-generar tickets al momento de programar funciones).
    *   Asíncronas: Escucha eventos en RabbitMQ (ej. Cancelaciones por emergencia del `Showtime Service`).

## 5. Estrategia de Concurrencia (Domain Logic)

Esta sección define el núcleo del negocio y la prevención de "Race Conditions".

### 5.1 El Ciclo de Vida del Ticket (Pre-generación)
**Regla de Arquitectura:** Los registros en la tabla `tickets` **NO se crean en el momento en que el usuario hace clic** en un asiento.

*   **¿Cuándo se crean?** Se pre-generan en bloque en el momento en que el Administrador crea la función (Showtime).
*   **Estado Inicial:** Todas las filas nacen con `usuario_id = null`, `estado = 'DISPONIBLE'` y `version = 0`.
*   **Beneficio:** Al pre-existir la fila, cuando múltiples usuarios intentan comprar al mismo tiempo, el sistema solo compite por hacer un `UPDATE`, permitiendo que las herramientas de bloqueo de la base de datos funcionen a la perfección.

### 5.2 Anatomía de las Columnas Especiales
*   **`estado` (El Semáforo del Negocio):** Etiqueta de texto (`DISPONIBLE`, `BLOQUEADO`, `VENDIDO`, `CANCELADO`).
*   **`version` (El Escudo de la Base de Datos - Optimistic Locking):** Contador numérico interno controlado nativamente por JPA/Hibernate (`@Version`). Impide matemáticamente que dos transacciones modifiquen la misma fila al mismo tiempo.
*   **`tiempo_bloqueo` (El Temporizador de Abandono):** Define el tiempo límite que un asiento puede permanecer en estado `BLOQUEADO` antes de liberarse.

### 5.3 Caso Práctico de Colisión: El Escenario "Juan vs. María"
¿Qué sucede cuando dos personas intentan comprar la **misma butaca** en el **mismo milisegundo**?
1.  **Petición de Juan (Llega primero):** PostgreSQL actualiza el ticket a versión 2.
2.  **Petición de María (Llega 2 milisegundos tarde):** PostgreSQL busca el ticket en versión 1. Ya no lo encuentra, porque Juan lo tomó. 
3.  **La Excepción:** Spring Boot detecta que se afectaron 0 filas y lanza una `OptimisticLockException`.

### 5.4 La Red de Seguridad (Garbage Collector con RabbitMQ)
¿Cómo garantizamos que un asiento bloqueado regrese a `DISPONIBLE` si el usuario no paga?
Se descarta el uso de Cron Jobs que saturen la base de datos con *polling*. En su lugar, se usa **RabbitMQ (Delayed Messages / Dead Letter Queue)**:
1.  **Bloqueo y Disparo:** Al momento de bloquear (`/api/seats/lock`), el Backend envía un mensaje diferido a RabbitMQ configurado para despertar en 5 minutos.
2.  **El Despertar:** Pasados los 5 minutos, el mensaje llega al `Seat Service`.
3.  **La Validación:** El Backend lee el `ticketId` del mensaje, consulta la base de datos y pregunta: *"¿Este ticket sigue en estado BLOQUEADO?"*.
    *   Si es `BLOQUEADO`: Significa abandono. El sistema lo fuerza a `DISPONIBLE`.
    *   Si es `VENDIDO` o `CANCELADO`: Significa que la venta fue exitosa o se liberó manualmente. El mensaje se ignora y se descarta de forma segura.
*   **Liberación Rápida:** Si el usuario presiona "Cancelar" o cierra la pestaña, el Frontend enviará un `POST /api/seats/unlock` para liberar la butaca inmediatamente sin esperar los 5 minutos. El mensaje de RabbitMQ igual llegará después, pero será ignorado con seguridad.

## 6. Manejo de Errores y Excepciones (GlobalExceptionHandler)

El servicio implementa un `@RestControllerAdvice` para estandarizar los errores, evitando trazas de Java en el Frontend.

### 6.1 Estructura del ErrorResponse (DTO)
```json
{
  "timestamp": "2026-06-24T10:15:30",
  "status": 409,
  "error": "Conflict",
  "message": "Lo sentimos, este asiento acaba de ser tomado por otro usuario",
  "path": "/api/v1/seats/lock"
}
```

### 6.2 Excepciones Específicas Capturadas
*   `OptimisticLockException`: Capturada internamente para devolver un mensaje amigable con código `409 Conflict`.
*   `FeignException / HttpClientErrorException`: Fallas al comunicarse con `showtime-service`. Devuelve `503 Service Unavailable`.
*   `IllegalArgumentException`: Errores de validación de negocio. Devuelve `400 Bad Request`.

## 7. Arquitectura de Validación Cruzada (Showtime State)

### 7.1 Validación de Red (Backend a Backend)
*   **Regla de Negocio:** Antes de cualquier bloqueo de asiento, el Seat Service llama al `showtime-service`. Si la función NO es estrictamente `PROGRAMADA` (ej. está en curso o finalizada), la compra es rechazada con un `403 Forbidden`.

### 7.2 Validación de UX (Frontend)
*   Si la función devuelta por el API Gateway está `EN_CURSO` o `FINALIZADA`, el Frontend ocultará el mapa de butacas mostrando: *"La venta de entradas está cerrada porque la función ya inició o terminó"*.

## 9. API Contract (Endpoints Internos)

> **Nota:** Estos endpoints son llamados por el API Gateway, quien expone la ruta `/api/v1/seats/` al Frontend.

### `GET /api/seats?funcionId={id}`
*   **Propósito:** Obtener el mapa de butacas para una función en específico.
*   **Respuesta Exitosa (200 OK):** Lista de tickets con su estado actual (`DISPONIBLE`, `BLOQUEADO`, `VENDIDO`, `CANCELADO`).

### `POST /api/seats/lock`
*   **Propósito:** Intentar bloquear una butaca temporalmente (Paso 1 del pago).
*   **Payload Esperado:** `{ "ticketId": 1502 }`
*   **Respuesta Exitosa (200 OK):** Butaca bloqueada con éxito.
*   **Respuesta Error (409 Conflict):** `OptimisticLockException` capturada, el asiento fue tomado.

### `POST /api/seats/unlock`
*   **Propósito:** Liberación explícita e inmediata de una butaca (Ej. el usuario se arrepiente y presiona "Volver" o cierra la pestaña).
*   **Payload Esperado:** `{ "ticketId": 1502 }`
*   **Respuesta Exitosa (200 OK):** Butaca devuelta a estado `DISPONIBLE`.
*   **Nota de Arquitectura:** Este endpoint es la vía rápida. Si falla o el usuario pierde conexión, el mensaje de RabbitMQ de 5 minutos actuará como red de seguridad (Garbage Collector).

### `POST /api/seats/redeem-coupon`
*   **Propósito:** Interceptar y aplicar un código de cortesía interno, bypasseando la pasarela de pagos.
*   **Payload Esperado:** `{ "codigo": "PERDON-A7X9", "ticketIds": [1502, 1503] }`
*   **Respuesta Exitosa (200 OK):** Cupón quemado y asientos cambiados a `VENDIDO`.

## 10. Acceptance Criteria (TDD Scenarios)

*   **Scenario 1: Bloqueo exitoso**
    *   **Given** un ticket `DISPONIBLE`.
    *   **When** se hace POST a `/api/seats/lock`.
    *   **Then** el estado cambia a `BLOQUEADO`, la versión incrementa y retorna HTTP 200.
*   **Scenario 2: Race Condition manejado correctamente**
    *   **Given** dos peticiones simultáneas para el mismo ticket.
    *   **When** ambas ejecutan la actualización.
    *   **Then** la primera retorna HTTP 200 y la segunda retorna HTTP 409 Conflict sin corromper la DB.
*   **Scenario 3: Liberación de asiento por timeout**
    *   **Given** un ticket `BLOQUEADO` cuyo `tiempo_bloqueo` ya fue superado.
    *   **Then** el cronjob interno o el *Dead Letter Queue* de RabbitMQ lo devuelve a `DISPONIBLE`.

## 11. Eventos Asíncronos y Patrón SAGA (RabbitMQ)

El Seat Service utiliza RabbitMQ como columna vertebral para dos flujos críticos que no pueden depender de la fragilidad de llamadas síncronas HTTP.

### 11.1 Flujo Feliz: Consolidación de Pagos (`PaymentSuccessEvent`)
Cuando la pasarela externa (Culqi) reporta un pago exitoso vía Webhook, no se llama directamente al Seat Service. Se dispara un evento a RabbitMQ.
*   **El Consumidor (`seat-service`):** Escucha el evento, toma la lista de `ticketIds` que venían en el payload, y los pasa oficialmente de estado `BLOQUEADO` a `VENDIDO`. La venta está finalizada.

### 11.2 Flujo Trágico: Cancelación por Emergencia (`ShowtimeCancelledEvent`)
En el mundo real, el Administrador puede forzar el mantenimiento de una sala incluso si hay funciones en curso.
1.  **El Disparador (`showtime-service`):** Cancela las funciones afectadas y publica el evento `ShowtimeCancelledEvent`.
2.  **El Consumidor Principal (`seat-service`):** Escucha el evento, busca los tickets afectados y cambia su estado a `CANCELADO`, invalidando los códigos QR.
3.  **Resolución Financiera (Bypass Interno):** Se genera un registro en la tabla `cupones` asignado al ID del usuario y se inicia el reembolso. En su próxima compra, el usuario ingresa el cupón en `/api/seats/redeem-coupon`, omitiendo la pasarela de pagos Culqi (Bypass).
